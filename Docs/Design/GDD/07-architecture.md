## 20. Архитектурные требования

Эта часть описывает способ реализовать уже утверждённые игровые правила. **Конкретный игровой движок, неткод, протокол и хостинг не выбраны окончательно**, даже если ниже даются рекомендации.

### 20.1 Требования к архитектуре

1. **Авторитет сервера.** Итоги перемещения, боёв, выдача XP/дропа, состояния босса и прогресс персонажей подтверждаются сервером.
2. **Закреплённый состав.** У сессии неизменяемый после запуска список `MemberCharacterIds`/`MemberAccountIds`.
3. **Сохраняемая сессия.** Игровой процесс можно выгрузить и восстановить без необходимости держать живым движок несколько суток.
4. **Разделение персонажа/мира.** Состояние изученной географии и предметов не сериализуется внутрь комнаты.
5. **Многозонность мира.** Подгрузка окружения и interest management без обязательного разбиения одной комнаты на несколько серверов.
6. **Конфигурируемый контент.** Профессии, монстры, формулы, навыки и босс-энкаунтеры желательно задавать данными.
7. **Версионирование.** Обновление клиента и серверного контента не уничтожает старые сохранения.
8. **Мобильная устойчивость.** Нормальная реакция на скрытие приложения, потерю связи, смену сети и возврат игрока.
9. **Наблюдаемость.** Логи, метрики боёв и реконструируемые причины наград.
10. **Минимальный вертикальный срез до большой архитектуры.** Избежать преждевременной разработки собственного полноценного сетевого движка.

## 21. Предлагаемый набор компонентов

**[ПРЕДЛОЖЕНО]** Стартовая техническая реализация:

```text
┌─────────────────────────────────────────┐
│ Unity Client (iOS / Android / Editor)   │
│ Input • Camera • Animation • HUD • FOW  │
└─────────────┬───────────────────────────┘
              │ Commands / State Updates
              ▼
┌─────────────────────────────────────────┐
│ Authoritative Game Server (per Session) │
│ Movement • Combat • Abilities • AI      │
│ Threat • Encounters • Zone simulation   │
└─────────┬────────────────┬──────────────┘
          │                │
     Saves/Events      Session control
          ▼                ▼
┌─────────────────┐  ┌────────────────────┐
│ PostgreSQL      │  │ ASP.NET Core API   │
│ Characters      │  │ Auth • Lobby       │
│ Inventory       │  │ Sessions • Join    │
│ Exploration     │  │ Save/Resume        │
│ WorldSnapshots  │  └────────────────────┘
└─────────────────┘
```

### 21.1 Игровой клиент [ПРЕДЛОЖЕНО]

**Unity 3D** — рабочая рекомендация, поскольку хотим изометрию, мобильную сборку, анимацию и C# код. Альтернативный движок отдельно не оценивался. Клиент отвечает за ввод, локальную камеру, HUD, рендер карты/тумана войны, интерполяцию движения, предсказуемую анимацию и отображение серверных событий.

### 21.2 Игровой сервер [ПРЕДЛОЖЕНО]

Рассматривались Unity dedicated server с готовой сетевой библиотекой/Netcode и собственный .NET game server. Для первой реализации **рекомендуется готовый сетевой слой**, а не создание синхронизации движения с нуля; выбор Netcode for GameObjects/Entities/другого решения нужно валидировать на нагрузочных прототипах.

**Важное разделение:** ASP.NET Core прекрасно подходит для аккаунтов, лобби, API персонажей и хранения результатов, но не обязательно должен сам выполнять высокочастотную симуляцию ударов и движения через обычные HTTP endpoints.

### 21.3 Сервис управления комнатами [ПРЕДЛОЖЕНО]

Модуль Session Manager обеспечивает создание лобби, проверку прав входа, формирование состава, запуск игрового процесса, сохранение, остановку и возобновление. Истинный состав проверяется по серверной учётной записи, не по произвольно переданному клиентом GUID.

### 21.4 Хранение [ПРЕДЛОЖЕНО]

PostgreSQL — подходящая кандидатура для персонажей, инвентаря, прогресса и метаданных комнат. Большие snapshots или карты исследования можно хранить в оптимизированных бинарных/blob представлениях; конкретное хранилище выберем после измерения размера данных. Не хранить весь Unity GameObject graph.

## 22. Доменные модули (логические границы)

| Модуль | Ответственность | Важные инварианты |
|---|---|---|
| Identity | Аккаунт, токен, право входа | Игрок доказал свою личность |
| Character | Уровень, опыт, класс, экипировка | Состояние принадлежит персонажу |
| ClassProgression | Ветки, испытания, навыки | Переход разрешён только при выполнении условий |
| Session | Лобби, roster, сложность, pause/resume | Roster не меняется после старта |
| World | Зоны, объекты, триггеры, состояние проходов | Мир один на комнату |
| Exploration | Открытые клетки, метки, Fog of War | История принадлежит персонажу |
| Combat | Урон, статусы, cooldown, попадания | Итоги рассчитывает сервер |
| Ability/Effects | Активки, пассивки, процы предметов | Эффекты с ограничениями и детерминированным порядком |
| AI/Threat | Состояния мобов, цели, преследование | Враг не действует вне правил зоны и видимости |
| Encounter | Фазы босса, условия победы, reset | При полной паузе незавершённая встреча сбрасывается |
| Loot/Rewards | XP, дроп, предметы, выдача | Только участникам и без повторной выдачи |
| Content | Таблицы баланса, мир, версии | Мигрируемое и отслеживаемое содержимое |

**[ПРЕДЛОЖЕНО]** На старте это **модули одного приложения или небольшого количества сервисов**, а не обязательные 12 микросервисов. Не начинать с распределённой инфраструктуры ради абстрактной масштабируемости.

## 23. Состояние игровой комнаты и персонажа

### 23.1 Пример C#-моделей [ПРЕДЛОЖЕНО]

```csharp
public sealed record CharacterProgress(
    Guid CharacterId,
    string ProfessionId,
    int Level,
    long Experience,
    long Revision);

public sealed record SessionRoster(
    Guid SessionId,
    IReadOnlyList<Guid> OriginalCharacterIds,
    int InitialPlayerCount,
    bool IsLocked);

public sealed record WorldSnapshot(
    Guid SessionId,
    string WorldVersion,
    int SaveSchemaVersion,
    IReadOnlySet<string> DefeatedBossIds,
    IReadOnlySet<string> UnlockedPassageIds,
    IReadOnlyDictionary<Guid, string> SafeRespawnPointByCharacter,
    long Revision);

public sealed record ExplorationChunk(
    Guid CharacterId,
    string ZoneId,
    int GridRevision,
    int ChunkX,
    int ChunkY,
    byte[] ExploredBits);
```

Это **схемы для обсуждения**, не готовая промышленная модель: реальные версии требуют транзакционных границ, обновления snapshot и согласования с профилем сохранения.

### 23.2 Отдельные данные персонажа и комнаты

- **CharacterProgress** — становится актуальным между комнатами, его нельзя откатывать при возобновлении старого мира.
- **WorldSnapshot** — содержит только комнатные факты; не сохраняет копию уровня и текущей экипировки каждого участника в качестве единственной истины.
- **ExplorationChunk** — сохраняется независимо от комнаты и может расширяться при добавлении новых `ZoneId`.
- **SessionRoster** — immutable после перехода к состоянию ACTIVE.

### 23.3 Потенциальный конфликт: одна постоянная личность — много комнат

**[ОТКРЫТО, важно решить до сетевого MVP]** Герой может участвовать в новых комнатах, сохраняя персонажа. Но если предыдущая комната ещё сохранена, как именно происходит возвращение? Предлагаемый вариант:

- Одновременно только **одна активная симуляция** для одного `CharacterId`.
- Старые сохранённые комнаты можно выбирать, но персонаж заходит в них со своим актуальным уровнем/экипировкой, а не откатывается к уровню из старого snapshot.
- Для изменения прогресса использовать optimistic concurrency / revision и блокировку активной сессии.
- Вопрос с точкой появления и текущим мировым статусом решать без изменения общей карты и без копирования дропа в старую комнату.

Эти правила нужно отдельно подтвердить: они предотвращают dupes, но влияют на баланс старых сохранений.

## 24. Псевдопроцессы

### 24.1 Создание комнаты

```text
POST CreateLobby → LobbyId
AddMembers / Invite / Ready
Host: Start
  → Validate roster and characters
  → Lock fixed member list
  → Set InitialPlayerCount
  → Create session world (known WorldVersion)
  → Start authoritative GameServer instance
  → Return connection credentials to original members
```

### 24.2 Подключение первоначального участника

```text
Join(SessionId, authenticatedAccount, CharacterId)
  → Is the session locked?
  → Does this account/character belong to the original roster?
  → Is the character currently active in another world?
  → ACTIVE: issue short-lived join token
  → SUSPENDED: restore server + world state, then issue token
  → Unknown character: DENY (even if slot is free)
```

### 24.3 Полная пауза и восстановление

```text
All participants disconnected
  → proposed grace period
  → lock new writes to this world during suspension
  → reset unfinished boss encounters to initial state
  → assign safe spawn points outside boss arenas
  → persist WorldSnapshot + reward journal state
  → stop inactive game simulation

Original participant returns
  → authenticate and verify roster
  → load snapshot / ensure world version compatibility
  → rebuild zones, mobs and completed world flags
  → spawn returning player at allowed safe point
  → resume session for remaining original members
```

### 24.4 Атомарная выдача награды

**[ПРЕДЛОЖЕНО]** Сервер формирует уникальный `EncounterCompletionId`/`RewardEventId`, проверяет eligible участников, затем одним атомарным процессом создаёт награду и обновляет прогресс героя. Повтор того же `RewardEventId` не выдаёт предмет ещё раз, даже если клиент переслал запрос или сервер упал после записи.

## 25. Зональная подгрузка и сетевой интерес

**[ПРИНЯТО]** Игрок видит единый мир, но технически зоны подгружаются. **[ПРЕДЛОЖЕНО]** Разделить три разных понятия:

1. **Content streaming на клиенте** — подгрузка геометрии/текстур/звуков ближайшей зоны.
2. **Simulation partition на сервере** — удобные границы AI, респавна и событий, без обязательной серверной изоляции каждой зоны.
3. **Interest management** — клиенту отправлять сущности и обновления, значимые для его позиции/радиуса, а не всю карту целиком.

**[ПРЕДЛОЖЕНО]** Один Game Server обслуживает одну комнату на старте. Это гораздо проще корректно синхронизировать и сохранять. Границы зон позже можно использовать для физического масштабирования, только если измеренная нагрузка потребует этого.

## 26. Конфигурация контента и эффекты

**[ПРЕДЛОЖЕНО]** На уровне данных описывать:

- `ClassDefinition`: идентификатор класса, родитель, доступные переходы, профили статов, умения, испытания.
- `AbilityDefinition`: target type, range, cooldown, cost, cast time, effect nodes.
- `PassiveDefinition`: событие-триггер, ограничение частоты, условие, эффект.
- `MonsterArchetype`: HP/урон/радиус обнаружения/связанная группа/набор умений/loot table.
- `EncounterDefinition`: набор фаз, HP-триггеры, действия, условие завершения.
- `ItemDefinition`: статы, требования, редкость, изменители умений.
- `ZoneDefinition`: bounds/biome/spawn points/соседства/обзор/предметы для подгрузки.

**[ПРЕДЛОЖЕНО]** Унифицированная система событий эффектов (OnHit, OnCast, OnDamageTaken, OnHeal, OnKill, OnPhaseChanged) позволит разделить абстракции умений, пассивок, предметов и боссов. Ограничивать вложенные пробы и рекурсию, чтобы комбинации «эхо вызывает эхо» не зависали.

**[ОТКРЫТО]** ScriptableObjects, JSON/YAML, внутриигровой редактор и формат контент-пакетов. Скрипты сервера и клиента должны опираться на одинаковые идентификаторы/семантику, даже если сериализация отличается.

## 27. Производительность и безопасность

### 27.1 Мобильные ограничения [ПРЕДЛОЖЕНО]

- Оптимизировать draw calls, память, число частиц и количество анимируемых объектов.
- Учитывать низкую частоту кадров при плотных AoE-сражениях.
- Использовать LOD/простые модели и читаемые текстуры без перегруза деталей.
- Во время фоновой работы приложения не симулировать локально неавторизованные движения персонажа.
- Не полагаться на то, что клиент всегда отправит корректный `Disconnect`.

### 27.2 Сетевые границы доверия [ПРЕДЛОЖЕНО]

- Проверять членство в roster по серверной аутентификации.
- Проверять cooldown/дальность/допустимую цель и состояния эффектов.
- Не доверять клиентским значениям опыта, предметов и урона.
- Защищать операции предметов от повторной выдачи/удаления при ретраях.
- Контролировать чрезмерную частоту команд движения и боя.

### 27.3 Мониторинг [ПРЕДЛОЖЕНО]

Логировать время старта/паузы комнаты, число участников, процент reconnect, длину сессии, частоту падений, длительность боёв, победы по разным составам, выдачу наград и размеры snapshots. Без телеметрии сложно проверить баланс профессий и последствия правила фиксированной сложности.

# 07. Сохранения и идентификаторы

## Согласованные требования

Исследованная география принадлежит персонажу и переживает переход между комнатами. После выхода всех игроков из игры во время боя с боссом следующий вход должен помещать их в безопасную зону вне арены. Эти правила требуют различать постоянные данные героя и временное состояние игровой сессии.

## Уточнение целевой модели по полному GDD

Разделы 3–4 подтверждают постоянство опыта, уровня, профессии, экипировки, предметов и географии за героем между комнатами. Победы над боссами, проходы и события относятся к отдельной комнате; её состав и исходная сложность фиксированы. При полной паузе незавершённый босс сбрасывает здоровье, фазы и угрозу, а победа над завершённым боссом сохраняется. Политика одного героя в нескольких сохранённых комнатах и недопущение одновременного активного входа ещё требуют решения. Это целевые правила; локальный PlayerPrefs ниже реализует лишь малую часть.

## Что сохраняется сейчас

Используется локальный `PlayerPrefs`. Единственный условный персонаж — `local-hero-001`; выбора героя и аккаунта нет. Исследование карты хранится отдельно от задания. Позиция, здоровье, экипировка и безопасная точка не сохраняются; герой при новом запуске появляется в (0, -9) по X/Z.

Ключ текущей географии: `TwilightGrove.exploration.v2.local-hero-001`. Данные — массив 96 × 96 байт, закодированный Base64. Каждая клетка указывает, исследован ли её участок. Дополнительного заголовка с регионом, размерами и контрольной суммой пока нет: совместимость определяется версией ключа и длиной массива.

Старый ключ: `TwilightGrove.exploration.v1.local-hero-001`, массив 64 × 64 байт. Если нового ключа нет, `GroveExploration` читает старый. Вложенная сетка помещается с отступом 16 клеток в центр новой. Поскольку оба варианта используют шаг 0,5 метра, координаты изученных областей сохраняются. Старые данные не удаляются, новое состояние отмечается для записи.

Проверка формата ловит некорректную строку Base64 и несовместимую длину, после чего начинается новая карта с предупреждением. Это ограниченная защита. Сейчас любые ненулевые байты считаются изученными; нет резервной копии и восстановления из предыдущего поколения.

Ключ задания: `TwilightGrove.quest.crystals.v1.local-hero-001`. Целое число хранит биты 0–4 для пяти кристаллов и бит 5 для завершения доставки. При загрузке флаг завершения принимается только вместе со всеми пятью кристаллами.

## Когда происходит запись

Исследование записывается только при наличии изменений, примерно раз в 2 секунды, а также при сворачивании, потере фокуса, отключении компонента и завершении приложения. Прогресс задания записывается сразу после каждого сбора, доставки и подтверждённого повторного старта. Используется `PlayerPrefs.Save()`.

При принудительном аварийном завершении последние клетки до очередного сохранения могут потеряться. Телефон и редактор имеют отдельные хранилища; Git хранит исходники, но не автоматически синхронизирует PlayerPrefs. Переноса прогресса на другой телефон и облачных сохранений нет.

## Предложение: структура данных персонажа

Выделить профиль с устойчивым `characterId`, версией схемы, состоянием заданий, словарём исследования по регионам и последней разрешённой точкой возвращения. Региону дать собственный `regionId`; ревизия карты не должна заменять личность персонажа.

Исследование хранить как `characterId → regionId → layerId → mapRevision → cells`. `layerId` понадобится для этажей. Для задания использовать постоянные ID квеста и интерактивных объектов, чтобы перестановка массива кристаллов не означала сбор другого объекта.

В прототипе `characterId` исследования задаётся полем компонента, а в задании зашит в константу. Перед добавлением второго героя нужно объединить источник идентичности: иначе карта и задание окажутся привязаны к разным героям.

## Предложение: сервис хранения

Сделать единый интерфейс загрузки/сохранения профиля. Первая реализация может оставаться локальной; компоненты не должны знать строковые ключи и формат файла. Это позволит позднее заменить хранилище без переписывания движения и задания.

Для файлового формата предусмотреть версию схемы, проверку размеров, резервную копию и атомарную замену файла. При серверном хранении определить право записи, обработку повторных запросов, конфликт устройств и источник истины. Конкретная база и формат ещё не выбраны.

Миграции документировать отдельным правилом: что меняется, какие значения переносятся, что сохраняется для отката. Не использовать общий сброс всех данных как стандартный способ обновления карты. Повторное тестирование задания должно менять только его состояние.

## Постоянное и временное

География и личный прогресс задания — постоянные данные героя. В будущем здоровье босса, активные атаки и временные эффекты должны относиться к состоянию комнаты/арены, если не принято другое правило. Последнее положение в арене нельзя без проверки считать разрешённой точкой входа.

При возвращении после сброса босса сначала выбрать безопасную точку, затем создавать игрока. Загрузка карты при этом независима: персонаж помнит арену, но не возобновляет прерванный бой.

## Проверки сохранений

Проверить неполный сбор, завершение, повторный сбор, перенос старой географии и повреждённые данные. Перед появлением нескольких героев проверить изоляцию профилей. Перед появлением комнат — переход туда и обратно без потери карты. Перед сервером — повторные запросы, разрывы соединения и отсутствие двойной выдачи награды.
